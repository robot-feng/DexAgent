# 场景重建子步骤、明确关联与审核时钟（2026-10-21）

本轮延续完整流程工作区，把场景重建内部结果接到真实清理任务，并修复视频审核中两边时间基准不一致的问题。复用现有 CleanupJob、运行报告、媒体端点和播放器，没有创建新的资产或任务注册表。

## 1. 界面与模块边界

「完整流程 → 场景与资产重建 → 结果预览」增加四个子视图：

- 场景结果：保留本次 Stage2 的重建预览。
- 背景与对象分离：查看明确关联任务的 mask、分割对象和来源视频。
- 背景补全：查看同一任务的补全输出；没有结果则保持未生成。
- 对象资产：查看本次 `stage2/assets` 中已索引的模型文件，文件存在不赋予物理验收资格。

清理任务页面用选择器代替不断增长的任务按钮列表，保留 `job` 深链接。模型/播种诊断与关键帧 overlay 可展开，整段视频审核更靠前。旧任务仍可直接通过 ID 打开。

## 2. 显式关联

`CleanupCreate.run_id` 可选；从某次运行进入分离页时，新建任务记录该运行。已有任务通过 `POST /background-cleanups/{id}/run` 明确关联或解除关联。

约束：

- 目标运行必须存在，创建前检查，避免无效关联启动 worker。
- 关联保存在原 `job.json`，不改输入视频或源报告，不批准 mask，不启动补洞。
- 清理阶段仍活动或 worker 尚未退出时拒绝修改关联，防止与 worker 写文件竞争。
- `GET /background-cleanups/jobs?run_id=...` 在筛选后取最近 30 项，避免较早的关联任务被无关任务挤掉。
- 前端再次核对任务 `run_id`，错误的深链接不能显示其他运行的结果。
- 关联只说明这个任务属于该重建运行，不证明扫描、演示与场景已配准；也不代替版本化 Scene / Demo / Task / Robot 绑定。

## 3. 原视频与审核视频的时间不同

实际 `ThrowAwayTrash.mp4` 源视频为 1072 帧、17.884533 秒；mask 为 400 帧、12 fps、33.333333 秒。旧界面按相同 `currentTime` 对照原视频和 mask，会显示不同操作时刻。

Stage1b 保存了来自同一抽样序列的 `s1_video/input_video.mp4`（400 帧、33.28 秒），但其容器时间格与 mask 仍有差异，不能据此宣称逐帧对应。

新增审核代理：

1. 从生成 mask 的原始抽样 PNG 序列按相同顺序编码，保持原视频及源产物。
2. 使用 mask 实际帧率生成独立 `input/review_source.mp4`。
3. 用 ffprobe 核对帧数、分辨率及全部逐帧 PTS。
4. 记录原始帧 hash、代理 hash、mask hash、帧率及最大 PTS 差到 `input/review_source.json`。
5. 只有代理与 mask 身份仍匹配时，API 才标记 `review_timebase=frame_aligned`；没有代理时回退到同源处理视频并标注 `approximate`，缺少处理视频时两边独立播放。

当前样例代理：400 帧、672×384、12 fps，与 mask 的全部 PTS 差为 **0**。代理 hash 为 `37990beb25f3d9df6f48bb12d62a93a224ccb7903ef9c70f076ebdc6f51d86b2`。

播放器的暂停跳转现在绕过播放时 120 ms 的漂移容差；12 fps 下单帧跳转约 83 ms，不会再被忽略。上述对齐标志只证明 mask 审核代理；背景补全输出在未核对其独立时钟前仍标注近似对照。
