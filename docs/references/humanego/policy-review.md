## What is directly useful

1. **An embodiment-independent observation/action seam, not a replacement task system.** A hand or object has a metric SE(3) pose; ICT packs the entity pose plus hand-to-entity relations. This is a useful policy observation/reference derived from Scene/Demo and current Robot state, complementary to our semantic task/success predicates. It does not encode task text, task goals, contacts or success verification by itself. Per-task training configs select task/dataset; the model takes no language input.
2. **Clean-image representation can reduce human/robot visual mismatch:** inpaint arm appearance and render a common virtual gripper/object keypoints. Existing scene clean-up remains necessary separately: these are observation images, not collision meshes or validated object-free background reconstruction.
3. **Relative hand/object geometry and phase/grasp information can drive multiple action sources.** Learned FM is an additional motion source; it can fit behind our existing action-source/backend contract. It produces end-effector targets and a grasp scalar, not source robot joint arrays and not full dexterous finger controls.
4. **Cross-session holdout is superior to random frames for adjacent video data.** Preserve recording/scene/object/person splits explicitly and retain provenance in our data exporter.
5. **Train/test encoding must be shared and tested.** Their separate Dataloader, utils/ict, deployment policy and visualization implementations have diverged; we should derive adapters from our existing calibration/action mappings rather than clone multiple versions.

## Policy architecture and tensor contract

- `training/FlowMatchingModel.py:41`: RGB encoder is a learned Conv2d patch embed, not DINO/SAM inside the policy. Example recipe is 240x320, patch16 -> 300 visual tokens, embed384, 6 decoder blocks, 8 heads. `:86` decoder combines action-query self-attention and cross-attention to ICT+image context. `:218` gives entity slots learned positional embeddings, so object order is part of the contract; arbitrary permutations are not automatically invariant.
- `FlowMatchingDataloader.py:211`, `:311`: token dimension20 single hand /29 dual hand: `[type1, entity pose9, hand-in-entity9 or18, flag1]`. Pose9 = normalized xyz + six rotation values. Type IDs0 pad,1left,2right,3anchor,4other. Hand flag is binary grasp; object flag−1. Hand slots first (missing hand retains masked zero slot), anchor next, then object dict iteration order; max8 defaults, excess silently truncated (`:390`).
- `utils/utils_math.py:112–149`: rotation6 is **row-major flatten of first two matrix columns**, i.e. `[R00,R01,R10,R11,R20,R21]`, and Gram-Schmidt inverse. This must not be confused with a concatenated-column convention used by some models. Position `(p−mean)/(std+eps)` is shared for global and relative translations; unpack by `p_norm*std+mean`.
- `FlowMatchingDataloader.py:279`: selected reference is inverse `metadata.world_transforms.virtual_static_anchor` or inverse `world_transforms.cam0`. It is not the currently rendered camera pose `metadata.c2w`. The latter is used independently for pixel projection. Upstream generation semantics must be retained.
- `:446–593`: targets start at **k=1**, future integer folder offset `k*stride`; action layout is **modality-major**: single `[pos3,rot6,grasp1]`, dual `[Lpos3,Rpos3,Lrot6,Rrot6,Lgrasp1,Rgrasp1]`. No per-future timestamp vector is consumed or emitted here. Default50 future indices is not intrinsically50 control ticks or50ms. Need sample period/resampling metadata when exporting to our policy/controller.
- Optional anchor-object dynamics adds9 prediction dimensions (`Model:202–205`), optional legacy done-in-flow adds1. Current separate done head predicts1 trajectory-level logit from pooled observation (`Model:272,390`), trained against the **last horizon** done flag (`Trainer:472–474`); it is not a physical success predicate.
- Optional MiniPointNet encodes64 points/entity (`Model:54`). Missing object keypoints fallback to center and replicate; hand cloud is repeated hand position (`Dataloader:294,355,370`). It is sparse geometry context, not mesh/contact geometry.
- Optional region attention adds Gaussian visual-token bias centered at projected anchor (`Model:295`). Optional visual foresight predicts future2D trace coordinates via MLP, **not heatmaps** despite stale comments/README (`Model:256,394,478`). Optional “temporal contrastive” is masked **MSE on future hand ICTs**, with no negatives/contrastive contrast set (`Model:485–497`). Do not copy marketing names as different mechanisms.
- `Trainer:456–464` trains linear conditional flow `x_t=(1−t)x0+t*x1`, vector target `x1−x0`; optional minibatch Hungarian noise matching at `:317`. Euler ODE inference `:596–601`. Weighted MSE positions/rotations/grasp plus optional aux/done BCE (`Model:404`). AdamW, EMA, cosine warmup, optional AMP.

## Dataset splits / normalization / validity limits

- `Trainer:69–82` discovers **every subdirectory**, not a name-pattern-checked list; `:85–136` picks first lexically sorted session of eval_source and takes next N as training. Under expected layout this is recording000. It keeps adjacent frames of that session out of training, but does not ensure different scenes, people, object instances, task variants or absence of duplicate/symlink content. No explicit overlap/dedup validation for custom paths.
- `Trainer:274–306` computes position mean/std only from training-path hand token positions, samples ~10k frames; uses default Aria hands rather than forwarding chosen hand_tracking_method. No validation against run split/config hashes when loading cached stats (`:762–770`).
- `--data_num` slices local `training_sessions` at`:758` but stats use **unsliced** cfg.MPS_PATHS_TRAIN at`:768`; limited-demonstration experiments can use distribution information from unselected training sessions. This is a normalization scope flaw, not proof of held-out eval leakage.
- Explicit `--train_data/--eval_data` paths are set at`:1239` but overwritten in `main` by data_sources or default non-null task autodiscovery (`:725–750`). README claim of arbitrary explicit lists is not reliably implemented.
- Dataloader `_frame_has_required_fields` (`:250`) only lightly validates dict/hand presence and optional image path key. It does not gate camera validity, 4x4 SE3, metric-scale proof, calibration, confidence, or even image file existence.
- `Dataloader:614–625`: legacy image path comes from JSON absolute path; newer path still derives directory from `obs.rgb_path`, not the actual loaded JSON parent. `utils/utils_io.py:174–182` silently substitutes all-black image on missing path. Download script extracts but does **not rebase JSON image paths**. For downloaded/moved precomputed data verify actual path validity before training; do not claim data already works locally from tar extraction alone.
- `Dataloader:266–274,483–494,528–533`: future lookup assumes contiguous numeric directories. Missing first future label remains zeros; later missing labels forward-fill. No target-valid mask is returned or used by loss. Last indexed frame can therefore supervise all-zero future rotation/position/grasp. Gaps/end-of-recording are not explicitly excluded.
- `Dataloader:511–515`: delta-action base is first available **future** hand pose, not observation at t. Visual evaluator composes predicted delta with current pose (`Evaluator:378,393`), creating a one-step anchoring mismatch. Released examples use absolute, so this concerns optional delta extension.
- `Dataloader:638–645` random image crop changes apparent pixel geometry but `anchor_uv` and trace targets are computed against uncropped intrinsics (`:702–711`,`:525–527`). If using region attention/foresight this is a geometric augmentation mismatch. Legacy interpolation also blends ICT between d0/d1 while future targets stay at integer offsets from d0 (`:692–714`); should be made explicit before porting augmentation.
- Object auxiliary latch uses dominant right hand in dual mode and a single anchor transform, reset per sample (`Dataloader:480,543–556`), not a contact-aware multiobject physical state estimator.

## Evaluation is not robot rollout / task acceptance

- `Trainer.eval_ode_inference:538` predicts from recorded observation batches and compares future hand paths. Metrics: weighted position distance, rotation geodesic, graspF1, done-label accuracy (`:659–683`). No robot model, engine, stepping, contact or task predicates.
- Dual position error is norm over concatenated six coordinates (not mean per-arm norm) `:615–616`; batch means then mean over batches can overweight short final batch (`:655–656`). No claim of mean physical task error should be based on this unchanged.
- `FlowMatchingEvaluator.py:231` is explicitly teacher-forced GT-vs-pred video; actual future GT/context available each frame; no predicted-state rollout. It passes default img_name/hand method/legacy behavior into dummy loader rather than forwarding all train options (`:245–256`).
- Its region anchor UV incorrectly derives from normalized xyz token coordinates (`Evaluator:107–123,198`) rather than actual camera projection used by train/numerical eval (`Trainer:468,596`). Thus its visualization can use different conditioning from numerical evaluation for region-attention checkpoint.
- Done prediction is learned label and drawn “TASK FINISHED” (`Evaluator:403`) without physical acceptance. Preserve independent task gates in EmbodiForge.
- `Trainer:871–887` auto-resume expects latest.pt contains optimizer. Local trainer saves it, whereas root README describes published stripped latest.pt plus latest_full.pt. Compatibility must be verified for downloaded resume weights; source doesn't select latest_full.pt automatically. EMA weights saved with original optimizer and EMA shadow reinitialized; exact deterministic training resume is not proven. `best` is initialized but never updated, score printed only; `train_history.json` read on resume but never written by current source.

## Deployment: useful template, material missing pieces

- `inference/interfaces.py:46,66,82,125`: Camera returns aligned **RGB-D**+K, arm returns EE pose and accepts Cartesian command, perception supplies object metric6DoF and clean images. OpenCV optical coords xright/ydown/zforward, meters, gripper0open/1closed. This is a fixed calibrated camera episode, not arbitrary monocular video producing metric poses unaided.
- `run_inference.py:135` estimate_objects **raises NotImplementedError**; all model construction commented. `:148` make_clean_image just copies raw frame. No shipped complete detect/pose/inpaint/render deployment in this template.
- `:229–247` hardware and policy constructed, initial perception called, arms homed before loop try/finally `:255`. This is not something to execute as a smoke command on shared hardware.
- `policy.py:110–116`: delta unsupported but prints warning rather than refusing; PCD checkpoint fed none with warning. Model auxiliaries build/load but object dynamics not used to update scene. `prepare_image:165` always feeds actual clean-image tensor; state-only training needs caller explicitly black image, not automatic flag handling.
- `run_inference.py:155–207` latches nearest initial object if gripper closed and center-distance<0.20m; contact/force evidence absent. Reinitializes dynamic objects from static initial poses each call, so released object resets to initial pose; both arms can latch same object, later side overwrites it. This is an occlusion hypothesis, not proof of grasp, placement or physical dynamics.
- **Anchor mismatch:** `policy.build_ict:205–206` takes current obj_states anchor to define ref, but `run:247,274,285` passes fixed initial anchor into projected attention and decode. If manipulated anchor changes, observation and action frames diverge. Training uses `virtual_static_anchor` so preserve that reference separately from moving anchor entity.
- `controller.py:58–75`: first command copied without distance clamp; later max_pos_step is relative to previous commanded target, not measured arm position. safe_z_min merely stored (`:50`), not forwarded; Trossen default floor−.12m enforced in driver (`RobotArmTrossen:207–227,508`). No collision/selfcollision check, contact verification, robust failure termination or trajectory validity in template.
- `controller.execute_chunk:78–102`: synchronous chunk execution then inference; effective perception/replan cycle is inference+8*0.1s default, not necessarily advertised5–10Hz fresh observations. `time.sleep(dt)` adds compute latency. Missing production async thread/ensembling explicitly documented in inference README and controller footer.
- **Grasp scalar semantics:** Dataloader encodes labels0/1 (`:522–523`), trains flow target0/1 (`Trainer:432–464`); evaluator (`:608`) and inference (`policy:298–310`) call sigmoid then threshold0.5. Any small positive residual for “open” becomes “closed”; target0 produces0.5 exactly, target1~0.731. F1 additionally >=0.5 (`Trainer:662`) makes exact0 prediction positive. Should establish scalar-vs-logit encoding consistently before porting.
- `run:291–293` done_prob terminates task without independent scene/task evidence. Our RSS verifier must remain authority and policy done only proposed termination.
- Config sample robotextrinsics are identity placeholders (`cfg/inference/example_dualarm/RobotArmTrossen*.yaml`), model.wxai, gripper0.045m,7joints. Its EE-to-Aria-hand T_align cannot be blindly applied to G1/G2 or56jointSharpa dexterous mapping.
- Trossen driver is substantial real SDK+GUI+leader/follower teleop, not a simulator. It applies a native-frame rotation correction `:311` plus base-to-camera extrinsic `:449–520`. `set_speed_limit` only stores an unused value (`:376`); startup errors swallowed; connection/hardware scripts not equivalent to qualified task execution.
- Camera driver handles real RGB-D alignment, crop-adjusted K, depth-unit scale, MAD-based depth filtering (`CamRS:18–63,112–120,283–400`). It stores host wall-clock **milliseconds** at`:225` while CamRSData comment says ns (`CamRSTypes:27`), has no timestamp in exposed Frame, and appends every frame to RAM (`CamRS:240`). Missing frame returns tuple instead of CamRSData (`:229`), adapter does not check. Empty serial config comment says first device but code rejects (`:123–132`). These need adapter validation, not cloning into monocular-first core.

## Minimal EmbodiForge integration recommendation

1. **Now: data/reference adapter**, not another platform: import a selected released session into existing Demo assets preserving raw video/path, per-frame camera pose/calibration, hand/object metric transforms, timestamp source, original scene/referenceframe identity, visibility/confidence, grasp/contact assumptions and source provenance. A benchmark can first validate geometry and cross-frame projections without installing training stack or claiming physical pass.
2. Derive **interaction observation** from existing semantic task/object IDs and demonstration geometry: hand/object relative6DoF, chosen fixed reference separate from moving anchor object, explicit relation/time validity. Keep raw finger tracking if available; do not replace Sharpa finger requirements with binary grasp.
3. Export training samples with real image paths, source-time dt, target-valid masks, source-scene split hash, normalization keyed by exact training IDs; preserve optional fixedanchor vs initialcamera frame choices; golden tests compare training observation and runtime observation bit-level geometry/layout.
4. Once input/retargeting physically accepted, add HumanEgo FM as **optional policy motion provider** through existing execution contract, with model config/hash/stats/frame/EE convention manifest. Reuse current RSS/controller/gates/Episode recording, do not use template done as task success or geometric latching as physical contact.
5. Qualify per target robot on same task/table. These assets/policy targets don't satisfy multiembodiment test on their own. All three baseline embodiments still need their own reachable motion/contact/control, reset+success+failure evidence.
6. Pretrained checkpoint reproduction separate from our monocular-first milestones; raw Aria training path and RGB-D deployment metadata should not be mislabeled a no-calibration ordinary RGB-only solution. No extra SDK/engine unification required to learn from the relation and observation design.
